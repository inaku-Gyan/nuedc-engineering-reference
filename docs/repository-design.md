# Repository Design

## 设计目标

本仓库同时服务三种行为：

1. **定位**：用型号、别名或问题快速找到资料。
2. **理解**：通过短摘要和专题摘录，在较小上下文内获得答案。
3. **核验**：需要精确参数时可回到版本明确的一手原件。

因此目录分为导航层 `catalog/`、资料层 `library/` 和知识层 `knowledge/`。

## 为什么资料按对象成包

按 `pdf/`、`markdown/`、`summary/` 分目录会让同一器件的信息分散，并使版本关系
难以判断。按对象成包后，摘要、原件、摘录和来源元数据共享一个边界，移动或作为
Git Submodule 引入时也更容易理解。

## 为什么不默认全文提取

全文提取会产生大量低价值文本、表格识别错误和重复内容，也会诱导 Agent 加载过多
上下文。以下情形才值得新增摘录：

- 经常需要查阅；
- 已在业务项目中实际使用；
- 原 PDF 文本层缺失或检索困难；
- 多页内容需要重组才能回答一个明确问题；
- 需要补充术语别名、适用范围或勘误说明。

摘录应按主题而不是按任意页数切块。

## 可扩展索引

早期由 `catalog/*.md` 维护高价值入口即可。资料包数量增长后，可读取所有
`meta.yaml` 生成以下派生索引：

- `catalog/generated/inventory.jsonl`：供 Agent 或脚本流式检索；
- 按型号、厂商、标签、文档类型生成的 Markdown 索引；
- 缺失摘要、失效链接、重复 ID 和未核验版本报告。

生成文件必须明确标记为派生结果，规范数据仍以资料包内的 `meta.yaml` 为准。

## Submodule 使用

业务仓库将本仓库作为 Submodule 引入后，应：

- 在业务仓库根 `AGENTS.md` 或当前用户提示中声明知识库路径；
- 仅在任务相关时读取知识库本地 `KNOWLEDGE_AGENT.md`，再从
  `catalog/README.md` 开始；
- 本地 `KNOWLEDGE_AGENT.md` 缺失时只读使用知识库，并提醒用户运行
  `configure_agent.py`；
- 只在确有需要时读取 `originals/`；
- 在业务仓库记录项目专属决策，本仓库只沉淀可复用知识；
- 通过资料包路径和文档版本引用知识，避免复制后失去来源关系。

可复制的集成提示见
[`parent-repository-integration.md`](parent-repository-integration.md)。
